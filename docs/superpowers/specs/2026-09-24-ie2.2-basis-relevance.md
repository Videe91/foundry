# IE2.2 — Basis vs Relevance invariants (normative)

Base: `5cba86df269b9abe867dc705f65ef069c72ed90c` (IE2.1 closed). Incorporates R31–R62.
Design only.

## 1. Audit — what the repository does today

Grounded in code at this head.

**Basis and relevance exist as vocabulary; nothing checks completeness.** IE2.1 validates
that a relation is *permitted*. Nothing anywhere walks a basis chain or a relevance path.

**The two planes have genuinely different lifeness, and no abstraction spans them:**

| plane | liveness is | existing mechanism |
|---|---|---|
| `state.objects` | `lifecycle is ACTIVE` and `authority ∉ {REJECTED, SUPERSEDED}` | `closure._is_current` |
| `state.semantic.claims` | the asserting `ASSERT_CLAIM` judgment is active | `semantic_view.active_judgment_ids` |
| `state.semantic.evidence` | **no liveness concept at all** | — |

IE2.2 reuses these three and invents no fourth.

**Evidence supersession does not invalidate claims.** `domain/evidence.py`: lineage "carries
NO semantic authority: a claim citing a superseded version is neither superseded nor flagged
by it." IE2.2 does not overturn this.

**The certified Slice-1 Requirement is `PROPOSED`**, carries **no `SERVES` edge**, and its
basis claim carries **`INFERRED`** authority. All three facts matter below.

**Scope applicability is already duplicated.** Four private definitions —
`closure._object_applies`, `application/handoff_v2._applies`, `package._applies`,
`domain/handoff_v2._object_applies` — plus inline copies in at least four more modules, all
implementing `scope == () or scope in obj.scope`. This is a pre-existing drift risk that R39
makes relevant (§7).

## 2. The central law (R32)

**Canonical authority is the baseline. Evidential proof is an additional requirement for
some kinds, never a substitute and never mutually exclusive.**

```
EVERY canonical intended-state object   →  legitimate authority           (baseline)
SOME kinds, by semantic meaning         →  + a lawful evidential basis    (additional)
```

IE2.1 already guarantees the baseline at canonicalization: human author, authenticated
actor, covering `AuthorityRecord`. IE2.2 adds the evidential requirement only where the
object's meaning is a claim about the world.

The failure this shape avoids: forcing empirical evidence into human choices. "We will not
build video calling" is not a claim evidence could confirm, and fabricated evidence to
satisfy an invariant is worse than no invariant. Multiple compatible proof sources may
coexist — a Goal may carry evidential rationale without being required to.

## 3. Invariants

**Basis**
- `I-BASIS-1` — every **active, canonical, applicable** object of a kind requiring evidential proof (§4) has a `DERIVED_FROM` chain terminating lawfully (§5).
- `I-BASIS-2` — every chain terminates at a lawful terminal: a qualifying `SemanticClaim` (§5) or a qualifying canonical `ProjectDecision` (§6).
- `I-BASIS-3` — `ASSUMPTION` may never appear anywhere in a basis chain, terminal or intermediate.
- `I-BASIS-4` — no `DERIVED_FROM` cycle (§8).

**Relevance**
- `I-REL-1` — for evaluated delivery scope `S`, every active canonical object **of a relevance-bearing kind** (§4a) applicable to `S` has a `SERVES` path reaching the unique root Intent for `S`.
- `I-REL-2` — every object on that path is **applicable to `S`** (§7). Not containment.
- `I-REL-3` — no `SERVES` cycle (§8).

**Root**
- `I-ROOT-1` — for evaluated scope `S`, **exactly one** active canonical `Intent` applicable to `S` (§6).

**Separation** — `I-SEP-1` (`DERIVED_FROM` never targets `INTENT`) is enforced in IE2.1.

## 4. Per-kind grounding (R40)

Baseline for every row: canonical authority, established at canonicalization (R33).

| kind | evidential basis | relevance | terminal for others |
|---|---|---|---|
| `INTENT` | not required; root | n/a — it *is* the root | never (`I-SEP-1`) |
| `GOAL` | optional | required | intermediate |
| `OUTCOME` | optional | required | intermediate |
| `REQUIREMENT` | **either**: directly authoritative, or evidentially derived (R37) | required | intermediate |
| `CONSTRAINT` / `PROJECT_BOUNDARY` | not required | required | intermediate |
| `CONSTRAINT` / `EVIDENCE_BOUND` | **required** | required | intermediate |
| `CONSTRAINT` / `EXTERNAL_MANDATE` | **required**, plus attestation (§10) | required | intermediate |
| `NON_GOAL` | not required | required | never a basis |
| `PREFERENCE` | not required | required | never a basis |
| `DECISION` | optional | required | **lawful authoritative terminal** (§6) |
| `ASSUMPTION` | n/a — a recorded presumption | **not required** | **never**, at any position |
| `CONTRACT` | legacy; IE2.2 adds no new semantics | legacy | legacy |

`REQUIREMENT` (R37): absence of `DERIVED_FROM` is lawful for a directly authorized
requirement. If it *declares* `DERIVED_FROM` edges, those must obey the basis rules — an
object does not get to cite a basis and then be excused from its validity.

`ASSUMPTION`: no `SERVES` path is forced merely because the frozen synthesis kind set happens
to include it. Its dependency on intent is expressed by `AFFECTS`, which IE2.1 already
permits and IE2.3 will traverse.

### 4a. Relevance-bearing kinds (R43)

`I-REL-1` applies to exactly these:

```
GOAL   OUTCOME   REQUIREMENT   CONSTRAINT   NON_GOAL   PREFERENCE   DECISION
```

Explicitly excluded, each for a reason rather than by omission: `INTENT` is the root;
`ASSUMPTION` expresses dependency through `AFFECTS`, not a forced `SERVES`; `ACTOR` is
context; `CLAIM`, `EVIDENCE`, `UNKNOWN`, `QUESTION`, `CONFLICT`, `RISK` are epistemic;
`METRIC`, `VERIFICATION_OBLIGATION`, `AUTHORITY_RECORD`, `AMENDMENT` are measurement or
governance. `CONTRACT` stays legacy and gains no generalized relevance rule.

**This set is written out deliberately and not derived from `INTENT_BEARING_SEMANTIC_KINDS`.**
That frozen set carries historical ontology baggage — it includes `ASSUMPTION` and
`CONTRACT` — and deriving relevance from it would let a frozen vocabulary dictate semantics
it was never meant to decide.

## 5. The evidential terminal (R35), and what verification found

Lawful evidential terminal — a `SemanticClaim` such that **all** hold:

```
claim exists in state.semantic.claims
AND claim.created_by_judgment_id ∈ active_judgment_ids(state.semantic)
AND every id in claim.evidence_ids exists in state.semantic.evidence
AND claim.authority is CANONICAL                   ← explicit, never an ordering
```

Evidence must be **present**, not newest; existing supersession law is untouched.

**Why `CANONICAL` only (R42).** Verification found that `OBSERVED` is **not** structurally
restricted to trusted observation: `admission.py` refuses only `CANONICAL` claims from
non-human reasoners, so a model may assert `OBSERVED` freely. The system therefore cannot
truthfully read `OBSERVED` as "independently trusted observation" without provenance or
attestation machinery it does not have. Admitting it would have let a machine-recorded
assertion become the factual premise of canonical intent while the record implied more.

**Explicit consequence, accepted rather than worked around.** The certified Slice-1 basis
claim carries `INFERRED`, so it is not a lawful terminal for future canonical intent. This
does not affect certification — that Requirement is `PROPOSED`, and canonical rules do not
reach it. It does mean the Intent workflow will eventually need a way to canonicalize a
factual claim when a model or research result must ground canonical intended state. **That
workflow is not solved in IE2.2a**, and inventing it here would be scope creep disguised as
completeness.

### 5a. One law, every writer (R45–R51)

The evidential-terminal law applies to **canonical intent regardless of which writer produced
it**. Validity never depends on the event path (not option B), and human authorship of an
`INFERRED` claim does not make the claim `CANONICAL` (not option C). Authorship and authority
stay independent.

**Canonical and deliverable are different properties (R45).** The frozen `HUMAN_STATED`
synthesis vertical assigns `CANONICAL` from authenticated human authorship plus covering
authority, and deliberately never consults basis-claim authority — reading it would be the
laundering C9/I22 forbids. That rule is preserved, untouched. Such a Requirement is
legitimately `CANONICAL` as an authorized assertion of intended state, **and** not delivery-ready
when its declared factual basis is unlawful: readiness reports `UNLAWFUL_BASIS_AUTHORITY`.

**The mirror protection (R49).** A `CANONICAL` basis claim never lends its authority to an
`AI_INFERRED` synthesized object; that Requirement stays `PROPOSED`. A strong basis cannot
upgrade generated intent, and a weak basis cannot downgrade authorized intent — it only
blocks its delivery.

**Enforcement timing differs; semantic truth does not.** The IE2 seam refuses an unlawful
canonical basis before append. Historical and frozen writer paths cannot be changed, so their
state replays unchanged and current-state readiness evaluates the identical law, turning an
invalid basis into a deterministic blocker.

**The legal exit is append-only (R51).** `SemanticClaim` is immutable; nothing is
"canonicalized in place". The repair is: a human asserts a new equivalent `CANONICAL` claim,
the affected Requirement is superseded or reconciled, and its replacement derives from the new
claim. Existing history stays intact.

**Fixtures (R46–R48).** Positive T11/T12 delivery stories predate IE2.2b and are re-expected
openly: the claim helper takes an `authority` parameter defaulting to `INFERRED`, and only
stories asserting canonical delivery request `CANONICAL`. Because a `CANONICAL` claim needs
covering human authority at assertion time, those stories record the `AuthorityRecord` before
asserting the claim (R47). T7 needs no change — it includes live claims regardless of
authority and carries `authority=claim.authority` into `BasisClaim` — and a regression pins
that (R48). The historical `INFERRED`-basis shape is kept as a negative readiness proof (R50).

## 6. Authoritative terminals and the root (R31, R34)

**`ProjectDecision` is a lawful terminal** when it is current, `CANONICAL`, and applicable to
the evaluated scope with its own relevance path. The authorized project choosing something is
itself the ground; fabricating evidential basis for a choice would be the same error as
demanding evidence for a `NonGoal`. A Decision may optionally carry evidential rationale, and
if present it remains traceable and must be valid.

Preserved from IE2.1: a Decision is not a Constraint, never sources `CONSTRAINS`, and never
enters `obligation_ids`.

**Root is per evaluated delivery scope (R31), not per project.** For scope `S`, exactly one
active canonical `Intent` applicable to `S`. So:

```
Intent-A scope=("billing",)  +  Intent-B scope=("security",)    legal
Intent-global scope=()       +  Intent-billing scope=("billing",)
        → evaluating "billing" sees two applicable roots → readiness blocker
```

Multiplicity blocks readiness; it never fails replay. Sub-intents stay unexpressible —
`SERVES` still excludes `INTENT` as a source.

## 7. Scope applicability (R39)

For evaluated scope `S`, every object on a `SERVES` path must **apply to `S`** under
Foundry's existing semantics — `scope == () or S in scope` — not literal containment. A
scoped Requirement may serve a project-wide Goal:

```
Requirement scope=("billing",) → Goal scope=() → Intent scope=()      legal
```

**The audit found this rule already duplicated in four private helpers plus inline copies.**
IE2.2 must not add a fifth. Recommendation: extract one shared domain helper taking a scope
tuple, use it in IE2.2c, and migrate existing call sites in a separate mechanical change
rather than smuggling a refactor into an invariant slice.

## 8. Cycles (R41)

New `SERVES` / `DERIVED_FROM` cycles are refused at forward admission, with bounded
visited-set traversal so a pre-existing historical cycle terminates and reports rather than
hangs.

**Stated without overselling:** under IE2.1's forward-only law a relation target must already
exist, so a purely new cycle is difficult to form sequentially through the seam. The check
matters for legacy graph shapes, dangling or re-introduced ids, and future write paths that
do not go through today's seam. It is cheap insurance, not the solution to a failure the
current seam readily produces.

Historical cycles replay and become deterministic blockers.

## 9. Authority is established, not leased (R33)

Authority is checked at the governance act that establishes canonical state. A canonical
object does **not** become invalid because the authorizing human's `AuthorityRecord` was later
retired:

```
Alice authorized Monday → Alice makes a canonical Decision Monday → Alice's authority ends Friday
⇒ the Monday decision stands until explicitly superseded, amended or reconciled
```

Consequences for the design: basis traversal does **not** re-prove authority for objects
already `CANONICAL` — being canonical *is* the record of that act, and the durable admission
event retains the author for audit. No projected authorship store is needed. Historical
canonical objects remain subject to the new basis/relevance readiness laws (§10) but are never
retroactively stripped of authority for a missing old record.

## 10. Historical readiness blockers (R38)

History always replays. Historical canonical objects that fail present-day rules are valid
history and not delivery-ready. Proposed deterministic blockers, each with a legal exit:

| code | condition | exit |
|---|---|---|
| `MULTIPLE_CANONICAL_ROOTS` | >1 canonical Intent applicable to `S` | supersede or re-scope one |
| `UNGROUNDED_CANONICAL_OBJECT` | a declared basis reaches no lawful terminal | supersede onto a lawful basis |
| `DEAD_BASIS` | chain reaches a claim whose judgment is inactive | re-assert the claim, or supersede |
| `UNLAWFUL_BASIS_AUTHORITY` | a basis node is not `CANONICAL` | human asserts a new equivalent `CANONICAL` claim; supersede the object onto it |
| `ASSUMPTION_IN_BASIS` | assumption anywhere in a chain | re-express as `AFFECTS`, supersede |
| `ORPHANED_CANONICAL_OBJECT` | no `SERVES` path to the root for `S` | add relevance via a superseding object |
| `BASIS_CYCLE` / `RELEVANCE_CYCLE` | historical cycle | supersede a participant |

Every exit is an existing lifecycle operation. None requires editing history.

## 11. `ConstraintFacet` proof (R36 — decision B1)

`AuthorityRecord` is **not** modified. For `EXTERNAL_MANDATE`, the canonical Constraint,
admitted by an authorized human carrying that facet, **is** the attestation. IE2.2 additionally
requires a lawful evidential basis.

The truthful guarantee, stated as it will appear in any record:

> An authorized human attested that this is externally imposed, **and** a valid evidential
> basis exists.

Not: "Foundry proved the source is external." IE2.1's rule that `HUMAN` provenance cannot
masquerade as `EXTERNAL_MANDATE` is preserved. No `source_ref` keyword heuristics.

## 12. Certified Slice-1 compatibility

Unchanged and untouched. The certified Requirement is `PROPOSED`, so canonical rules do not
reach it; basis validation reads **object-local `DERIVED_FROM` relations**, never
`DerivationEdge`, so the two parent-id conventions never need reconciling here. Normalization
stays in IE2.3. Nothing is backfilled.

## 13. Enforcement layer per rule

| rule | layer |
|---|---|
| relation legality, `I-SEP-1` | admission (IE2.1, done) |
| `I-BASIS-4`, `I-REL-3` (new cycles) | **admission** |
| `I-BASIS-1/2/3`, `I-REL-1/2` for a **new canonical** object | **admission, gated on `CANONICAL`** |
| facet proof (§11) | **admission, gated on `CANONICAL`** |
| `I-ROOT-1` | **v2 delivery readiness** — history may hold several roots (IE2.2c) |
| basis failures in current state (§10, IE2.2b) | **v2 delivery readiness only** (R52–R54) — never `evaluate_closure` |

Non-canonical objects stay unconstrained: a Requirement proposed before its Goal exists is
normal incremental work.

## The real hazard (R44), verified

The fixtures in the previous draft were **impossible**, and the repository says so directly:

```
admit A ──SERVES──▶ B   (B absent)
→ UnresolvedTargetError: relation target 'B' exists in no permitted namespace
```

IE2.1 requires every relation target to resolve, so `admit A→B` then `admit B→A` cannot
happen: either B already exists and the second admission fails as a duplicate, or B does not
and the first admission fails outright. A self-edge fails the same unresolved-target rule.
Claiming these as REDs would have manufactured a failure the seam cannot produce.

**The genuine hazard is a legacy or dangling historical graph completed by a new write.**
Historical objects may carry relations that were never validated, including edges to ids that
do not exist. A later admission can close such a path into a cycle:

```
historical (replays fine):   A ──SERVES──▶ B        B does not exist
new admission:               B ──SERVES──▶ A        target A resolves, so IE2.1 permits it
resulting graph:             A → B → A
```

This is why **reaching the candidate's id is enough**, even when that id is currently
dangling: admitting `B` is precisely what would make the dangling edge real.

## RED tests

1. `ModuleNotFoundError: foundry.domain.graph_cycles`.
2. Legacy dangling `A ──SERVES──▶ B` + new `B ──SERVES──▶ A` is **currently admitted**.
3. Legacy dangling `A ──DERIVED_FROM──▶ B` + new `B ──DERIVED_FROM──▶ A` is currently admitted.
4. Legacy `A → B → C` with `C` dangling + new `C ──▶ A` is currently admitted.
5. A pre-existing historical cycle has no safe-termination behaviour, because the helper does not exist.

## GREEN proofs

- two-node `SERVES` closure refused; two-node `DERIVED_FROM` closure refused;
- three-node closure refused;
- a refused admission appends **zero** events and leaves the store byte-identical;
- an unrelated pre-existing cycle terminates safely **and does not refuse the new write** — `X ──▶ A` where `A ↔ B` cycle exists but `X` closes nothing;
- diamond DAG accepted — reconvergence is not a cycle;
- a long acyclic chain accepted;
- only the **same** relation type participates: a `SERVES` path plus a `DERIVED_FROM` path must not combine into a false cycle;
- both certified ledgers replay unchanged; legacy cyclic/dangling streams replay unchanged.

## Mutation controls

1. cycle check removed from the seam;
2. `SERVES` checking removed;
3. `DERIVED_FROM` checking removed;
4. visited set removed (killed by the unrelated-historical-cycle test);
5. traversal depth capped at 1 (three-node cycle passes);
6. dangling candidate-id target ignored (the real hazard stops being caught);
7. an unrelated pre-existing cycle treated as the candidate's cycle (over-refusal);
8. diamond reconvergence treated as a cycle (over-refusal);
9. `DerivationEdge` substituted for object-local `DERIVED_FROM`;
10. cycle validation moved into the reducer/replay (breaks legacy replay).

## Remaining decision

None. The evidential terminal set was decided as `{CANONICAL}` (R42), and the placement of
basis blockers as v2 delivery readiness only (R52).

# IE2.2b — grounding / basis completeness (as built)

Scope: `I-BASIS-1/2/3` and the facet proof (§11), at the seam and at readiness. Relevance,
roots and Decision applicability are IE2.2c.

## Placement (R52–R56)

```
evaluate_closure         = canonical/structural contract closure          unchanged
build_intent_package     = canonical contract projection                  unchanged
IntentDeliveryReadiness  = is that closed contract safe to hand downstream now
```

Closure may be closed and the package may build while v2 `deliverable` is `False` because of
a basis defect. This is required by the Slice-1 **P4** law, which remains authoritative.

`IntentDeliveryReadiness.basis_blockers: tuple[BasisBlocker, ...]` — ids only
(`code`, `object_ids`), deliberately not `ClosureBlocker`. `deliverable` additionally
requires `not basis_blockers`. v2 refusal exposes each category by name, in this order:

```
CLOSURE_NOT_MET  DISPUTED_LOCUS  PENDING_MATERIAL_JUDGMENT  UNRECONCILED_STALE_OBJECT
UNGROUNDED_CANONICAL_OBJECT  DEAD_BASIS  UNLAWFUL_BASIS_AUTHORITY  ASSUMPTION_IN_BASIS
BASIS_CYCLE  INCOMPLETE_SYNTHESIS
```

One semantic law (`domain/basis.py`), two timings: `record_intent_object` refuses a new
`CANONICAL` candidate before append; historical and frozen writers replay unchanged and
readiness evaluates the same function over every current, `CANONICAL`, scope-applicable
object. Frozen synthesis production code is not modified.

## Chain rules (R57–R59)

- `GOAL`, `OUTCOME`, `REQUIREMENT`, `CONSTRAINT` inside a `DERIVED_FROM` chain must be current
  and `CANONICAL`, and the chain must continue to a lawful terminal. A directly authorized
  Requirement with no `DERIVED_FROM` is lawful; another object citing it cannot stop there.
  `SERVES` says why something matters; `DERIVED_FROM` says why it is grounded.
- Every declared branch must be lawful; one good branch never hides a dead basis, a
  non-`CANONICAL` claim, an assumption, a cycle or an invalid intermediate.
- `EVIDENCE_BOUND` / `EXTERNAL_MANDATE`: additionally, at least one lawful chain reaches a live
  `CANONICAL` `SemanticClaim`. A `ProjectDecision` alone is not sufficient.
- **Stated limitation (R59):** a `ProjectDecision` is accepted as a terminal when current and
  `CANONICAL`. Its scope applicability and its `SERVES` path to the evaluated root are
  **not** checked in IE2.2b; they belong to IE2.2c.
